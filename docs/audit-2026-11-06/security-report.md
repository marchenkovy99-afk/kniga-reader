# Libra: отчёт по безопасности

Дата: 6 ноября 2026. Аудит ограничен проверенной областью. Это не сертификация OWASP ASVS и не утверждение об отсутствии всех уязвимостей.

## Подтверждённые результаты

### S01. Medium: внешние ресурсы EPUB позволяют отслеживать открытие книги

Локальная тестовая книга содержала изображение, CSS import и iframe на `audit.invalid`. Перехватчик запросов зафиксировал обращения. Они были отменены внутри изолированного браузерного контекста, реального получателя и пользовательских данных не было. Выполнение вставленного script/onerror не подтвердилось: запрет скриптов EPUB уже действовал.

Исправление: CSP ограничивает script/style/img/font/frame/connect; сторонние изображения, стили и фреймы книги блокируются. Локальные и data/blob-ресурсы, а также подключения к собственному Supabase разрешены. Политика встроена в offline HTML и конфигурацию HTTP заголовков текущего выпуска; исходная production-сборка также получает CSP. Добавлены `nosniff`, `Referrer-Policy: no-referrer`, запрет встраивания внешним сайтом. В Chromium и WebKit тест больше не фиксирует ни одного обращения к `audit.invalid`, текст книги доступен. Побочный эффект: книги, зависящие от ресурсов в интернете, не загрузят их; встроенные файлы продолжают работать.

### S02. Medium: FB2 принимал DTD и пользовательские сущности

До исправления проверенная parser-функция принимала XML с внутренним объявлением ENTITY. Подтверждена чрезмерно широкая разрешённая XML-конструкция. Чтение файлов ОС, серверный XXE, утечка через внешнюю сущность или успешный DoS не подтверждены и не заявляются.

Исправление: предварительное отклонение DTD/ENTITY до DOMParser, с исключением литеральных CDATA/комментариев; ограничение длины XML 50 MiB. Выполнены parser-регрессия и браузерная проверка отказа без сохранения неполной книги.

### S03. Critical по npm advisory: уязвимые зависимости среды тестирования

Исходный lockfile содержал Vitest 3.2.7, транзитивный Tinypool и @vitest/mocker. npm audit сообщил 2 Critical и 1 Moderate записи зависимостей. Это результат сканера и затронутые development-пакеты; эксплуатация против приложения или рабочей машины не проверялась и не утверждается.

Обновлено до точной версии Vitest 5.1.0, обновлён lockfile. `npm audit` после изменения не сообщает известных уязвимостей. Проверены отдельно исходная Libra и пакет тестов сохранённого выпуска. Приложение не использует тестовый worker в production.

Проверенные advisory из исходного результата npm: [Tinypool worker options](https://github.com/advisories/GHSA-5gmw-xhrv-c9v3), [Tinypool run options](https://github.com/advisories/GHSA-85c8-ppgw-ccpr), [Vitest traversal](https://github.com/advisories/GHSA-82fw-gwwq-j7x9), [mock registration](https://github.com/advisories/GHSA-qxg6-89mg-rqv8).

### Целостность синхронизации

D01–D04 имеют риск утраты доступа к действительным правкам и отката состояния. Исправлены и проверены на исходной логике и извлечённых функциях именно текущего собранного приложения с fake-indexeddb. CAS, серверные ревизии, приватное хранилище и существующая схема сохранены. Доказательство клиентской гонки не означает доказанный межаккаунтный доступ на сервере.

### S04. High: локальная смена аккаунта могла раскрыть и удалить книгу другого аккаунта

Подтверждено на точных исходных функциях и функциях фактического выпуска через fake-indexeddb. A сохраняет книгу, затем B подключает свою библиотеку; книга A скрыта. Запоздавшее изменение избранного/обложки/сохранение с ID A создавало привязку B. После этого B видел исходные приватные байты, мог поставить их в очередь своей синхронизации и удалить файл также для A. Отдельно воспроизведено переключение непосредственно между IDB-проверкой доступа и конечным чтением книги.

Исправление: захват владельца, проверка привязок внутри write-транзакции перед сохранением/удалением/избранным/обложкой, повторная проверка в конечном асинхронном обработчике, прерывание запрещённой транзакции. Начавшийся импорт копирует FileList до await и передаёт исходного владельца до сохранения; подключение библиотеки повторно проверяет аккаунт после ожиданий. Исходные байты и схема базы сохранены. Тесты доказывают отсутствие новой привязки B и сохранение содержимого A. Это клиентский дефект изоляции, а не доказанный обход RLS сервера.

Локальная граница доверия остаётся прежней: IndexedDB не шифруется приложением, а выход сохраняет скачанные байты. Проверки защищают штатный интерфейс и очереди синхронизации, но не владельца браузерного профиля с доступом к инструментам разработчика или файловой системе.

Исправление предотвращает новые случаи. Наличие или отсутствие прошлой утечки на рабочем устройстве не устанавливалось; чужие данные и исторические привязки не читались и не очищались автоматически.

## Рабочий Supabase: только чтение конфигурации

Проверен проект `qwnkigorqsgugcctnfmj`, таблица `public.libra_records` и bucket `libra-files`. Не читались записи книг, профили, сессии или файлы пользователей.

- RLS таблицы включён; SELECT ограничен `auth.uid() = user_id`.
- INSERT содержит проверку владельца; UPDATE содержит и USING, и WITH CHECK по владельцу.
- Storage SELECT/INSERT ограничены собственным UUID-каталогом; bucket закрыт, лимит файла 52,428,800 байт.
- `libra_compare_and_set` и `libra_guard_record` работают как SECURITY INVOKER с пустым search_path; CAS использует текущий auth.uid и ожидаемую ревизию. Trigger запрещает смену владельца/ключа, отмену tombstone и замену уже закреплённого hash.
- Supabase advisor сообщил отключённую проверку скомпрометированных паролей. Это настройка усиления защиты, не доказательство взлома; не менялась для общего проекта. [Описание настройки](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
- Ключ в клиенте `sb_publishable_*` является публичным клиентским идентификатором и сам по себе не секрет. Авторизация должна обеспечиваться RLS.

Активное BOLA/IDOR-тестирование рабочих API, создание пользователей в production, изменения auth/RLS, подбор паролей и проверки лимитов нагрузки не проводились. Для полного допуска нужны два изолированных настоящих тестовых аккаунта в staging и проверка GET/INSERT/UPDATE/DELETE/RPC/Storage с подменой user_id, ключей, путей и устаревших токенов. Проверка конфигурации подтверждает наличие правил, но не заменяет этот прогон.

## Границы проверки

Покрывались категории WSTG аутентификации/авторизации, клиентского ввода и конфигурации; ASVS access control/input validation/data protection; API Top 10 BOLA, authentication, resource consumption, misconfiguration. [WSTG](https://owasp.org/www-project-web-security-testing-guide/), [ASVS](https://owasp.org/www-project-application-security-verification-standard/), [API Security 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/).

Не выполнены: полный набор WSTG/ASVS, DAST внешней production-инфраструктуры, fuzzing ZIP/EPUB на больших объёмах, проверка всех браузерных CVE, реальные истёкшие/отозванные токены в staging, rate-limit и массовые нагрузки, физический захват сессии. Лимиты распаковки произвольных EPUB требуют отдельного усиления; ZIP-bomb эксплуатация не подтверждалась.

Решение: исправления повышают безопасность, но полная готовность к production пока не подтверждена из-за отсутствия соответствующих исходников выпуска и незавершённых проверок реальных устройств/изолированной серверной среды.
